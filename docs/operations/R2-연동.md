# R2 직접 전송·CDN 연동

2026-11-03 사용자 지정 리소스 기준. 버킷 생성/공개 상태는 사용자 확인과 첨부 화면을 기준으로 하며 S3 API 실검증은 자격증명 등록 후 수행한다.

| 용도 | 버킷/도메인 | 접근 |
|---|---|---|
| 업로드 검증 전 `pending/`·비공개 PDF/파일 | `blog-storage` | 비공개, r2.dev·custom domain 공개 OFF |
| 검증된 공개 이미지 `objects/` | `public-blog-storage` | 공개 이미지 전용 |
| 공개 CDN 주소 | `https://public-blog-r2.codelily.kr` | 위 공개 버킷의 Custom Domains에 연결, Active 확인 |

`blog-r2.codelily.kr`는 처음 제시한 도메인이며 현재 공개 파일 설정에는 사용하지 않는다. 비공개 버킷에 공개 도메인을 연결하지 않는다. 버킷 이름과 도메인은 별개이고 R2 버킷 이름에는 점을 넣지 않는다.

## 1. CORS

R2 → `blog-storage` → Settings → CORS Policy에 [private-cors.json](../../infra/r2/private-cors.json)을 붙여넣는다. 허용 origin은 `https://blog.codelily.kr`, 메서드는 PUT/GET/HEAD, 요청 header는 Content-Type, 노출 header는 ETag다. CORS 설정만으로 파일이 공개되지는 않는다. 운영 버킷에 개발 origin을 자동 추가하지 않는다.

`pending/` prefix에 1일 만료 Object lifecycle을 설정한다. 실제 설정은 대시보드에서 확인하고 기존 파일 retention과 혼동하지 않는다. 공개 버킷에는 업로드를 직접 허용하지 않고 서버 검증 후 copy만 수행한다.

## 2. S3 자격증명

R2의 Manage API Tokens에서 Object Read & Write 권한으로 `blog-storage`와 `public-blog-storage` 두 버킷만 선택한다. 앱에 Admin Read & Write/전체 계정 권한을 주지 않는다. S3용 **Access Key ID·Secret Access Key**가 필요하며 Caddy DNS API token 또는 Tunnel token을 재사용하지 않는다.

서버 저장소 루트에서 다음을 대화형으로 실행한다. PC에서는 기존 SSH 키로 `ssh -t` 접속 후 실행한다.

```sh
python3 scripts/configure-r2.py
```

Account ID는 R2 계정의 32자리 식별자다. 기존 Tunnel과 같은 Cloudflare 계정이면 첫 항목에서 Enter로 서버에 기록된 account ID를 사용할 수 있다. 다른 계정이면 해당 R2 account ID를 직접 입력한다. 버킷·도메인 기본값은 위 표와 같으므로 같은 구성이면 처음 네 항목을 Enter로 진행한다. 각 항목은 즉시 검증하며 잘못된 항목만 다시 입력받고 입력한 값은 오류 메시지에 출력하지 않는다. 두 S3 credential은 화면에 표시되지 않게 입력한다. 기존 앱 env를 보존하고 mode 0600으로 원자적 갱신하며, 기존 R2 값이 있으면 자동 교체하지 않는다. 비밀값은 채팅·Git·명령 인자에 넣지 않는다. 이 도구는 컨테이너를 재시작하지 않는다. 환경 파일 변경 후 앱을 재생성해야 실행 환경에 반영된다.

입력 도구 회귀 검증은 `python3 -m unittest discover -s tests -p r2_setup_test.py -v`로 실행한다. 도메인 입력 직후 원인 불명 종료가 보고된 상황을 계기로 도메인 자체의 유효성·앞선 항목 즉시 재입력·오류 내 값 비노출·계정 기본값을 검증한다.

이 앱은 기본 jurisdiction의 `https://<account-id>.r2.cloudflarestorage.com`을 사용한다. EU/FedRAMP 전용 jurisdiction 버킷이면 실제 endpoint를 먼저 확인해 adapter를 별도 보완한다. 공개 CDN 도메인으로 서명 PUT/개인 다운로드를 보내지 않는다.

## 3. 공개 이미지 CDN 캐시 규칙

공개 버킷 Custom Domain이 Active인지 확인한다. 공개 key는 `objects/<uuid>`처럼 확장자가 없어 기본 캐시 대상이 아닐 수 있다. **공개 R2 hostname에만** Cloudflare Cache Rule을 추가한다.

```text
(http.host eq "public-blog-r2.codelily.kr"
 and starts_with(http.request.uri.path, "/objects/")
 and http.request.method in {"GET" "HEAD"})
```

- Cache eligibility: Eligible for cache.
- Edge TTL: Cache-Control이 있으면 따르고 없으면 bypass하는 옵션.
- Browser TTL: 원본 Cache-Control 존중.
- 앱은 공개 객체에 `public, max-age=31536000, immutable`을 설정한다. 바뀐 이미지는 새 UUID를 사용한다.
- `blog.codelily.kr` HTML·인증 API·비공개 R2 endpoint를 이 규칙에 포함하지 않는다. 공개 이미지는 인증 쿠키에 따른 개인 콘텐츠를 반환하지 않는다.
- r2.dev는 공개하지 않아도 Custom Domain을 사용할 수 있다. r2.dev를 production CDN 주소로 쓰지 않는다.

## 4. 전송과 검증

브라우저 → S3 서명 PUT(private pending) → 서버 HEAD/서명/ETag 검증 → public copy → CDN GET이다. 큰 파일 본문은 VPS를 경유하지 않는다. 검증용 HEAD·최대 512바이트 prefix GET과 S3 server-side copy 등 API 제어 요청은 서버에서 실행한다.

SDK 자동 CRC32가 본문 없는 presign 단계에서 빈 파일 checksum을 넣는 문제를 오프라인으로 재현했다. `requestChecksumCalculation: WHEN_REQUIRED`로 불필요한 checksum을 제거하고 서명에 Content-Type/Content-Length를 고정했다. 파일 형식·크기·소유권·ETag 검증은 유지한다. 공개/비공개 버킷을 같은 이름으로 설정하면 adapter가 거절한다.

설정 뒤 실제 확인할 항목:

- [ ] 실제 계정/버킷 접근 및 private 익명 접근 거절
- [ ] 유효한 presigned PUT·CORS preflight·완료 검증
- [ ] 공개 이미지 CDN GET, 반복 요청의 HIT·Age·원본 Cache-Control
- [ ] 서명 개인 다운로드·오류 형식/크기·경합 거절
- [ ] Google 로그인 후 실제 에디터 이미지 업로드/삽입(별도 OAuth 설정 필요)

업로드 설정을 배포하기 전 실제 이미지 build/transfer와 운영 env 적용을 확인한다. 코드 수정·버킷 생성만으로 연동 완료라고 표시하지 않는다.

실계정 검증용 `scripts/verify-r2.ts`는 운영 DB/회원 세션을 만들지 않는다. `R2_VERIFY_WRITE=1`을 명시했을 때만 UUID 기반 작은 이미지/PDF fixture를 해당 두 버킷에 생성하며, 끝나면 이 실행에서 생성한 정확한 key만 삭제한다. 공개 테스트 이미지가 CDN에 캐시된 경우에는 만료/purge 전까지 캐시가 남을 수 있다. 키·서명 URL·응답 본문은 로그에 출력하지 않는다.

아래 `MIGRATOR_IMAGE`는 현재 검증한 release의 migrator image ID/digest로 설정한다. 서버에서 새 이미지를 빌드하지 않는다.

```sh
: "${MIGRATOR_IMAGE:?검증한 migrator image ID 또는 digest를 설정하세요}"
docker run --rm --network codelily_egress --env-file infra/env/code-lily.env \
  -e R2_VERIFY_WRITE=1 "$MIGRATOR_IMAGE" node --import tsx scripts/verify-r2.ts
```

이 검증은 bucket 접근·CORS preflight·실제 PUT·공개 복사/내용 일치·서명 비공개 다운로드·익명 S3 거부·악성 형식 거절을 확인한다. 캐시 규칙까지 적용한 후 `-e R2_VERIFY_CDN=1`도 추가하면 실제 CDN HIT를 필수 조건으로 삼는다. Google OAuth를 통한 앱 API 소유권/에디터 사용은 별도 인수다. 공통 S3 제어 요청에는 연결 3초/요청 10초 timeout과 최대 2회 시도를 둔다.

## 추가 비용 없이 권장하는 조치 순서

### 1. SSH를 키 인증 전용으로 전환

기존 root 세션과 iwinv 복구 콘솔 접근 수단을 유지한다. `ubuntu` 등 관리자 계정에 승인된 공개키를 등록하고 **별도 새 연결에서 키 로그인과 sudo를 먼저 검증**한다. 그 뒤 비밀번호 인증과 keyboard-interactive 인증을 끄고 최종적으로 root 직접 로그인을 금지한다. 전환 중 root 키 접속을 잠시 유지해야 한다면 `PermitRootLogin prohibit-password`를 중간 단계로 쓸 수 있다.

Ubuntu의 include 파일은 앞에서 결정된 값이 우선할 수 있다. 현재 `50-cloud-init.conf`에도 비밀번호 허용 설정이 있으므로 파일 하나를 추가했다는 사실만으로 완료하지 않는다. `sshd -t`, `sshd -T` 및 필요한 `-C` 조건 검증 → reload → 별도 신규 로그인 성공 → 기존 세션 종료 순서로 진행한다. 현재 VS Code 원격 사용이 보여 TCP forwarding을 일괄 차단하는 것은 보류한다. SSH 포트 변경은 이 조치를 대체하지 않는다.

### 2. 보안 패치 적용과 지속 운영

외부 복구 자료를 확보하고 iwinv 콘솔 접근을 확인한 뒤 APT 목록 갱신, 업데이트 적용 계획 시뮬레이션, 실제 패치, 필요 서비스 재시작·커널 재부팅을 정비 시간에 수행한다. OpenSSH·OpenSSL·sudo·커널을 우선 검토하되 의존 라이브러리를 임의로 분리 적용하지 않는다.

자동 패키지 목록 갱신과 unattended 보안 업데이트를 활성화하고 **무통보 자동 재부팅은 끈다**. 자동 업데이트도 needrestart에 의해 서비스를 재시작할 수 있으므로 일정과 재시작 정책을 함께 검토한다. 재부팅 뒤 SSH·시간 동기화·Docker 컨테이너·Tunnel·원본 TLS·공개 응답을 확인한다. 호스트 APT 업데이트만으로 고정 digest 앱/DB/Tunnel 이미지 내부 라이브러리가 갱신되지는 않는다. 이미지는 개발/CI에서 재빌드·검증 후 교체한다.

### 3. 불필요한 수신 허용 제거

같은 서버의 다른 서비스가 80·443을 사용하지 않는 점을 재확인한 뒤 **ELCAP inbound의 전체 IP 80·443 허용만 제거**한다. 현재 Tunnel·DNS-01 구성에는 이 허용이 필요 없다. 등록된 SSH 관리 IP 2곳은 실제 사용하는지 확인한 후 필요한 곳만 유지한다. outbound 7844·443·DNS·NTP/NTS를 혼동해 닫지 않는다.

후속으로 호스트 방화벽에 SSH 관리 source 허용과 기본 수신 거부를 추가할 수 있다. 기존 세션·롤백 수단을 유지하고 Docker 네트워크와 IPv6를 함께 검증한다. Docker nft 규칙 전체 초기화나 UFW만으로 공개 Docker 포트가 안전하다는 판단은 금지한다.

### 4. 기존 장비로 외부 백업과 복원 확인

이미 보유한 개발 PC 저장공간과 포함 트래픽 범위에서 암호화한 PostgreSQL 논리 백업 및 필요한 복구 설정을 서버 밖으로 보관하고 격리 환경에 복원한다. 새 유료 snapshot·백업 상품은 신청할 필요가 없다. PC가 꺼져 있으면 자동 백업이 멈추므로 성공 시각/실패를 확인하며, 서버 내부 volume 복사만으로 외부 백업 완료라고 하지 않는다. R2 객체와 DB의 일관된 복구는 별도 정책이 필요하다.

### 5. 무료 WAF 한도 내에서 쓰기 경로 보호

현재 기본 관리형 WAF는 유지한다. Free의 사용자 지정 규칙 5개와 속도 제한 1개 범위에서 **`http.host eq "blog.codelily.kr"`로 한정**해 로그인 시작/쓰기 API를 보호할 수 있다. Google callback·공개 GET·R2 서명 PUT을 일괄 challenge하지 않는다. `/api/auth/*` 전체를 같은 낮은 임계값으로 막지 말고 실제 요청 패턴을 보고 설정한다. 기존 naraebi에 영향을 주는 zone 전체 변경은 피한다.

앱 소스에도 인증 요청 60초당 최대 60회와 DB 기반 제한, 업로드 작성자 권한·10MiB/파일·시간당 20건·소유권·실제 형식/크기 검증이 구현돼 있다. 이는 CDN의 단일 제한 규칙과 역할이 다르며 실제 OAuth/에디터 인수를 대체하지 않는다. 동시 예약·크기 변경 경합 등 남은 인수 항목을 계속 유지한다. Bot Fight는 현재 꺼져 있으나 정상 자동 요청과의 호환 확인 없이 일괄 켜지 않는다.

### 6. 가벼운 운영 관측과 추가 격리

기존 systemd timer 등으로 디스크·inode·OOM·readiness·백업 최신 시각·인증서 만료를 관측하고, 제한된 maintenance 계정의 데이터 보존 작업을 예약한다. journal 용량 상한도 설정한다. 무료 검사는 추가 대형 모니터링 스택 없이 시작할 수 있다. 실제 알림 전달 채널과 비용은 별도로 확인한다.

Caddy/Tunnel의 capability 제거·no-new-privileges·PID 상한과 읽기 전용 rootfs는 쓰기 경로를 분리한 테스트 후 적용한다. 앱 ISR cache와 Caddy 인증서 volume을 막는 일괄 read-only 전환은 하지 않는다. HSTS는 blog 호스트에 한정해 짧은 max-age부터 검증하며 includeSubDomains/preload를 바로 적용하지 않는다. CSP는 Report-Only 평가와 Next.js·SunEditor·R2 이미지·Google 로그인 검증을 거친다.

## 다음 시작점과 미해결

1. SSH 키 전용·관리자 계정 전환 → 패치·필요 재부팅 → ELCAP 불필요 웹 수신 허용 제거 및 외부 백업/복원 준비.
2. 변경 후 SSH·시간·Docker·Tunnel·원본 HTTPS·공개 응답 재검증. 이번 점검만으로 조치 완료 표시하지 않음.
3. [502 진단](Cloudflare-502-진단.md)을 이어서 수행하고 Google 최초 OWNER 로그인·로그아웃·실제 에디터 이미지 업로드를 인수한다.
4. 앱/이미지 취약점 전수 검사, MFA/복구 수단, R2 lifecycle, 백업/복원, 자동 인증서 갱신 관측은 별도 미검증이다.

## 검증 방법과 근거

실서버 SSH의 `sshd -T/-t`, `ss`, `nft list ruleset`, APT 설정·로컬 python-apt 후보 집계, Docker inspect의 비밀값 제외 필드·top·stats, DB 역할/권한 SELECT, Redis 무인증 PING, 파일 stat, journal의 인증 결과 집계를 사용했다. iwinv 연결 서버의 ELCAP inbound/outbound와 Cloudflare 현재 보안 화면을 직접 읽었다. 공개 경로는 개발 PC GET 및 제한된 8개 TCP 포트 연결로 확인했다. 설정 변경·DB 쓰기·실제 인증·업로드는 실행하지 않았다.

- [Ubuntu 자동 업데이트와 재부팅·서비스 재시작](https://ubuntu.com/server/docs/how-to/software/automatic-updates/): 자동 패치와 자동 재부팅/서비스 재시작은 별도 정책이다.
- [Cloudflare WAF 공식 가용성 표](https://developers.cloudflare.com/waf/#availability): Free Managed Ruleset과 무료 속도 제한 1개 제공을 확인했다. 실제 계정 UI에서도 Free·0/5·0/1을 확인했다.

공식 문서 검색 도구는 503으로 실패해 공개 공식 문서를 브라우저로 확인했다. Cloudflare 토큰 API 조회와 최초 대시보드 조회는 자동 승인 검토가 범위 부족으로 거절했다. 토큰 조회는 실행하지 않았고, 사용자의 명시적 추가 승인 후 대시보드의 요금제/WAF/속도 제한만 읽었다. 차단된 동작을 우회하지 않았다. 외부 메시지 발송은 없었다.

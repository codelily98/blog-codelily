## 빌드와 최초 배포

1. lockfile을 포함한 검토된 소스를 CI에 가져온다. Node 24 이미지·배포 이미지 digest를 고정한다. 운영 DB나 OAuth secret을 빌드 단계에 주입하지 않는다.
2. `npm ci`, typecheck, boundaries, unit/integration test, browser 검사를 통과시킨다. `npm run build`는 공개 ISR 페이지를 요청 시 생성하도록 준비하므로 운영 DB 없이 실행된다. 현재 Windows 환경에서 Turbopack 작업 프로세스 오류가 있어 지원되는 Webpack 경로를 고정했다.
3. `infra/Dockerfile`의 build/runtime·migrator target을 사용한다. monorepo standalone의 실제 진입점은 `apps/code-lily/server.js`다. `public`이 추가되면 runtime 이미지에도 포함해야 한다. 현재 배포 자산은 `.next/static`이다.
4. 서버에는 Compose·비공개 env·secret 파일을 준비하고 이미지를 pull한다. `scripts/setup-production.mjs`가 비밀 파일을 생성하고 기존 값은 보존한다. 새 `pgdata`는 Compose의 두 init script가 runtime/migrator/maintenance를 분리한다. `bootstrap.example.sql`은 수동 provisioning 참고용이며 자동 init과 중복 실행하지 않는다. 기존 DB는 별도 이관한다.
5. migrator 계정 URL로 `npm run db:migrate` 또는 일회성 migrator 이미지를 실행한다. 같은 서비스 migration은 직렬 실행한다. migration 후 `schema_migrations` runtime의 INSERT/UPDATE/DELETE 권한을 회수하고 readiness용 SELECT는 유지한다. 스키마 소유자·다른 앱 권한 차단을 실제 PostgreSQL에서 확인한다.
   `002_rate_limit_retention.sql` 이후에는 새 maintenance 이미지를 예약에 사용하기 전에 `post-migration.sql`을 적용한다. 초기 가동 전 대상 수는 `lastRequest`가 현재보다 24시간 이상 오래된 행의 건수만 읽어 확인한다. 속도 제한 키와 원문 IP는 출력하지 않는다. 기존 일일 예약에서 가장 오래된 행부터 최대 5,000건을 정리하므로 잔량과 다음 예약 성공을 확인한다. 운영에는 적용했으며 재구축할 때도 백업과 격리 검증 후 같은 순서를 따른다.
   탈퇴 공개 관리가 들어간 앱 이미지는 `003_member_withdrawal.sql`과 `004_withdrawn_post_visibility.sql`을 먼저 적용한 뒤 기동한다. 롤백 시 이미 탈퇴 처리된 데이터의 `NULL` 작성자·본문 삭제 표시를 해석할 수 있는 앱 이미지를 사용한다. 처리 전 DB 백업을 직접 복원하는 경우에는 완료된 탈퇴를 재적용한 뒤 연결한다.
   파일 처리 도구 실행 전 `005_withdrawal_upload_settlement.sql`을 적용한다. 보존된 공개 파일의 `NULL` 소유자는 새 앱 계약의 일부다. 복원한 DB에서는 운영 트래픽 연결 전에 완료된 파일 처리 기록을 검증·재적용한 뒤 회원 탈퇴를 재적용한다.
   Work가 포함된 앱과 maintenance 이미지는 `006_work.sql`과 최신 `post-migration.sql` 적용 후 사용한다. Work 휴지통 정리 함수는 maintenance에만 실행을 허용하며 runtime 실행·maintenance 본문 조회는 차단한다. 이미지 롤백 시 추가 Work 테이블을 보존한다.
6. runtime env에는 `code_lily_runtime` DB URL을 넣는다. Google, R2, 내부 요약 token, telemetry secret도 비공개로 제공한다. runtime에 superuser/migrator credential을 넣지 않는다.
7. Cloudflare Tunnel·Caddy·DB·앱을 시작하고 `/health/ready`, 공개 글, Google 로그인·로그아웃, 역할별 관리, R2, CDN cache, 인증서 검증을 수행한다.
8. 최초 운영 데이터는 관리 UI에서 작성하거나 별도 검토한 이관 절차로 반영한다. 개발 seed를 운영에서 실행하지 않는다.

현재 Compose는 code-lily 하나를 배포한다. resume-site/intro-page/admin-dashboard는 후속 구현이며 가짜 이미지로 실행하도록 추가하지 않았다. Redis는 현재 앱의 필수 의존성이 아니고 선택 `cache` profile이다. profile 여부와 관계없이 Compose 변수는 해석되므로 예제의 이미지 변수는 실제 사용할 검증된 값으로 준비한다. 모든 host port는 비공개다.

## 변경과 rollback

새 필드 추가 → 호환 앱 배포 → backfill → 관찰 후 구필드 제거 순서다. 이미지 rollback은 이전 digest로 수행하지만 파괴적 DB migration은 이미지 rollback만으로 되돌아가지 않는다. 배포 전 복구 지점을 기록한다. 단일 호스트 장애까지 무중단이라고 표현하지 않는다.

## 백업·보존

- 초기 RPO 제안: 일간 논리 백업 기준 최대 24시간. 더 작아야 하면 base backup+WAL/PITR를 구성한다.
- 초기 RTO 목표: 2시간, 실제 복원 연습으로 검증한다.
- DB 백업은 암호화해 일일 실행하며 현재 보관 기준은 7일이다. 역할·권한·필요 설정·인증서 자료도 복구 사본에 포함한다. PC 외부 수신과 해시 검증을 수행하며 4주 주간 보존은 현재 적용한 정책에 포함하지 않는다.
- R2 객체는 DB 참조와 복구 시점이 어긋날 수 있으므로 불변 key를 사용하고 원본 삭제 유예·백업/복구 정책을 별도로 운영한다. public 객체도 유일한 백업으로 간주하지 않는다.
- `npm run db:maintain`은 원본 방문 이벤트 30일·감사 90일·만료 세션/검증 정보·마지막 요청 후 24시간이 지난 인증 속도 제한 행을 항목별 한 번에 최대 5,000건씩 정리한다. Work는 30일이 지난 말단 노드를 최대 500개 정리한다. 전용 유지보수 계정과 일일 systemd timer를 사용하며 삭제 대상 기준과 실제 삭제 완료 시각을 구분해 누적량을 확인한다.
- Docker stdout은 10MiB × 3으로 회전한다. 14일 같은 기간 보존이 필요하면 외부 수집기의 수명 정책을 함께 설정한다.
- 매월 격리 환경에서 복원하고 글·회원 세션 정책·About·개인 파일 접근까지 확인한다. 완료한 탈퇴 요청이 있으면 백업 시점 이후의 기록을 [탈퇴 복원 절차](Google-OAuth-공개준비.md#회원-탈퇴-접수와-운영-처리-순서)에 따라 재적용하고 세션·공개 화면을 검증한 뒤 트래픽을 연결한다.

## 장애 대응

DB 장애는 제한된 대기 후 오류 응답으로 종료하고 쓰기 성공으로 응답하지 않는다. 이미 생성된 공개 ISR 화면은 캐시가 남아 있으면 제공될 수 있다. Google 장애는 로그인에, R2 장애는 파일 기능에 한정한다. Tunnel 실패 시 공개 서비스가 중단되므로 connector 상태를 감시한다. 컨테이너 unhealthy는 자동 재시작과 같지 않다. readiness·OOM·재시작 횟수·디스크·트래픽·인증서 만료를 별도로 관측한다.

실 PostgreSQL 역할 격리·외부 암호화 백업과 격리 DB 복원·Tunnel/WAF 기본 인수는 운영 이력에서 확인한다. 부하·월간 복원·ACME 갱신 장기 관측은 후속 과제이며 로컬 통합 결과로 완료 처리하지 않는다.

## Compose 관리 명령

로컬 환경은 Root `compose.yaml`을 사용한다. 최초에는 `npm run local:setup`, `docker compose up -d --wait`, `npm run db:migrate`, `npm run db:seed` 순서로 준비한다. PostgreSQL 16과 Redis의 검증된 digest를 고정했으며 localhost에만 포트를 노출한다. `web` profile이 실제 Linux standalone 앱을 실행한다.

```sh
docker compose --profile web up -d --build --wait
docker compose --profile web ps
docker compose --profile web logs --tail=100 code-lily
docker compose --profile web stop code-lily
docker compose --profile web down
```

운영은 `infra/.env`에 digest를 설정하고 `infra/env/`에 runtime·migrator·maintenance 전용 환경 파일을 분리한다. release마다 앱과 migrator 이미지 버전을 맞춘다.

```sh
docker compose --env-file infra/.env -f infra/compose.production.yml config --quiet
docker compose --env-file infra/.env -f infra/compose.production.yml up -d postgres
docker compose --env-file infra/.env -f infra/compose.production.yml --profile tools run --rm migrate
docker compose --env-file infra/.env -f infra/compose.production.yml exec -T postgres psql -U postgres -d codelily_production -v ON_ERROR_STOP=1 < infra/postgres/post-migration.sql
docker compose --env-file infra/.env -f infra/compose.production.yml up -d code-lily caddy tunnel
docker compose --env-file infra/.env -f infra/compose.production.yml logs --tail=100 code-lily
docker compose --env-file infra/.env -f infra/compose.production.yml --profile tools run --rm maintenance
```

`down`은 보통 volume을 유지한다. `down -v`, image/volume 전체 삭제는 정기 배포나 새 PC 설정에 포함하지 않는다. 이번 세션의 전역 초기화는 사용자의 명시적 요청에 따라 한 번 수행한 작업이다.

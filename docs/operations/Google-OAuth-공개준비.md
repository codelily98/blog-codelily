# code-lily 일반 회원 공개 준비

## 2026-11-07 신규 가입과 기존 로그인 분리

- `/sign-in`의 Google 로그인은 기존 회원 세션만 생성한다. 기존 회원은 브라우저나 기기를 바꿔도 동의 화면 없이 로그인할 수 있다. 미가입 Google 계정이 이 경로를 사용하면 `signup_disabled`로 가입 안내를 표시한다.
- 신규 회원은 `/sign-in?mode=signup`에서 만 14세 이상임을 직접 확인하고 이용약관에 동의한 뒤 Google로 가입한다. 서버는 명시적 가입 요청의 두 boolean 값이 모두 참인지 확인하고 검증 버전을 OAuth 서버 상태에 연결한다. 회원 생성은 이 상태가 있을 때만 허용한다. 기존 계정과 역할은 그대로 사용한다. [Better Auth의 명시적 가입 옵션](https://better-auth.com/docs/concepts/oauth#disableimplicitsignup)
- 가입 절차는 서버의 계정 생성 여부를 기준으로 하며 DB 스키마는 동일하다. 두 확인값은 OAuth 상태의 수명을 따른다. 기존 OAuth 흐름에서 시작한 신규 회원은 가입 화면에서 다시 진행할 수 있다.

### 가입 연령 확인 구현과 검증

`/sign-in`에서 이용자가 만 14세 이상임을 직접 확인하면 로그인 버튼을 활성화한다. 헤더·댓글의 로그인 버튼은 이 화면으로 연결한다. 서버의 `/sign-in/social`은 엄격한 boolean 확인값이 없는 요청을 거절하며, 검증한 버전을 OAuth 서버 상태에 연결한다. 신규 사용자 생성에서도 해당 서버 상태를 확인한다. 자기 진술에 대한 확인이며 실제 연령 인증으로 표시하지 않는다. 기존 세션을 임의로 종료하거나 기존 회원의 생년월일을 추정하지 않는다.

확인값과 버전은 기존 OAuth 상태의 수명을 따르며 회원 테이블에 생년월일·신분증·새 연령 필드를 저장하지 않는다. 직접 ID 토큰 경로 등 필요한 서버 상태가 없는 신규 생성은 거절한다. 진행 중이던 이전 버전 OAuth 신규 가입은 재시작이 필요하다. 로그인 오류 화면에서 다시 확인하도록 안내한다. 기존 역할 지정은 검증 이메일 기반 OWNER·그 외 MEMBER 정책을 유지한다.

타입·경계·단위/SQL 테스트 24개와 프로덕션 빌드를 통과했다. 격리 테스트는 실제 Better Auth의 상태 생성·서명 쿠키·callback·사용자 DB 생성 경로를 사용하고 Google 토큰 교환·사용자 정보 응답만 합성했다. 확인 누락의 사용자 생성 거절, 확인 후 MEMBER 생성과 입력한 OWNER 역할 무시를 검증했다. 실제 Google 신규 가입과 구분한다. Chrome에서는 기존 회귀 7개와 새 가입·정책 흐름 1개를 검증했다. 1440×1100·390×844의 정책·가입 화면에서 자동 접근성 위반과 가로 넘침은 없었다. 새 소스는 아직 운영에 배포하지 않았다.

### 실계정·Google 도메인 인수

운영자가 지정한 별도 Google 계정으로 직접 로그인한 뒤 서버의 MEMBER 역할을 확인했다. 실제 화면에서 합성 공개 문서 검색 1건과 정제 본문, 회원 API의 빈 원문, 비공개 상위 폴더 아래 공개 문서의 직접 URL 거절, 휴지통 API의 관리자 권한 거절을 확인했다. 기존 업무일지를 포함한 비공개 트리는 노출되지 않았다. 테스트 당시 공개 Posts가 0건이므로 실제 회원 댓글 인수는 완료하지 않았다.

운영자는 유일한 OWNER를 유지하고 같은 검증 계정을 MEMBER 확인 후 EDITOR로 변경하도록 명시 승인했다. 운영자 전용 접속에서 검증 이메일·기존 역할을 잠금 안에서 대조하고 역할과 기존 앱 형식의 감사 기록을 한 트랜잭션으로 갱신했다. 같은 Google 로그인 세션의 서버 역할이 EDITOR로 바뀐 것을 확인했다. 계정 이메일·내부 ID는 이 문서에 저장하지 않는다.

Google Console은 운영 계정으로 연결됐다. 홈페이지·정책·약관 URL은 당시 비어 있었고 Testing 상태였다. Search Console에서 도메인 속성 접근이 거절돼 DNS 확인 절차를 준비했으며, 실행 직전 운영자의 명시 승인을 받았다. Cloudflare의 `codelily.kr`에 Google 검증 TXT 1개(TTL 자동)를 추가하고 Search Console의 **소유권이 확인됨** 결과를 확인했다. 기존 TXT는 0개였고 웹 연결 레코드는 변경하지 않았다. 인증 유지에 필요한 TXT를 임의로 삭제하지 않는다. Google 브랜딩 검증·일반 게시와 도메인 확인은 별개다.

이어서 Testing 앱의 홈페이지 `https://blog.codelily.kr/`, 개인정보처리방침 `https://blog.codelily.kr/privacy`, 약관 `https://blog.codelily.kr/terms`를 저장하고 Console의 저장 완료 메시지와 세 값을 확인했다. 현재 연결되는 운영 정책은 기존 검토본이다. Audience를 일반 게시하거나 브랜드 검증을 제출하지 않았다.

공개 업체 문서는 [Cloudflare DPA](https://www.cloudflare.com/cloudflare-customer-dpa/)와 [Google 개인정보처리방침](https://policies.google.com/privacy?hl=ko)을 확인했다. 이후 운영자는 업체 문구의 작성을 위임했다. [iwinv 약관·SLA](https://www.iwinv.kr/treaty/treaty/all)와 [개인정보처리방침](https://www.iwinv.kr/treaty/treaty/person), [Cloudflare 서비스 약관](https://www.cloudflare.com/terms/), [네트워크 소재지](https://www.cloudflare.com/network/), [R2 위치 문서](https://developers.cloudflare.com/r2/reference/data-location/)도 대조해 검토 페이지를 작성했다. 국내 인프라 호스팅과 운영자 DB 관리, Cloudflare의 HTTP 요청·파일 처리, Google 로그인과 Gmail 문의의 목적·항목·시점·방법·운영 보관 기준·거부 영향을 구분했다. 개별 파일·요청의 특정 국가 보장, 별도 계약 체결, 업체 자체 기록의 삭제 상한은 추정하지 않았다.

Cloudflare 공개 Self-Serve 약관 6.1의 DPA 편입 설명에는 EU·UK·California 데이터 등 적용 범위가 명시돼 있으며, 공개 DPA는 v6.4(2026-04-03)로 표시된다. 이 링크만으로 한국 개인정보의 처리위탁 계약 요건이나 이 계정의 체결 사실을 충족했다고 판단하지 않는다. Google 일반 로그인·Gmail을 Google Workspace 계약으로 간주하지 않는다. 서비스 제공에 필요한 계정 처리는 개인정보 보호법 제15조 제1항 제4호 검토 대상이고, 국외 처리위탁·보관은 제28조의8 제1항 제3호의 필요성·고지 항목 등 실제 요건을 대조해야 한다. 이것은 적용 검토 기준이며 적법한 이전 근거가 이미 충족됐다는 확정이 아니다. [개인정보 보호법](https://www.law.go.kr/lsInfoP.do?lsId=011357)

### 승인된 합성 항목 정리 결과

자동 승인 검토가 운영 데이터 삭제의 구체적 승인이 없다는 이유로 실행을 차단했다. 운영자가 이번에 만든 합성 문서·폴더 3개에 한해 삭제→복구 후 비공개 확인→휴지통 이동을 명시 승인해 차단을 해소했다. 초기 명령의 runtime 환경 파일명 오류는 데이터 변경 전에 종료됐으며 실제 Compose 파일명으로 수정했다.

배포된 동일 migrator 이미지의 Work application 서비스를 최소 권한 runtime DB로 실행했다. 실제 EDITOR 역할의 생성·이름 변경·이동·공개 설정·삭제·복구·저장·미리보기·휴지통·일지 생성 **10종 거절**, 회원 원문 숨김과 상위 폴더 차단, OWNER의 복구 후 비공개를 확인했다. 이 결과는 실제 서버의 application 서비스 직접 호출이며 브라우저의 모든 HTTP 쓰기 요청을 실행한 것으로 기록하지 않는다.

합성 3개를 휴지통으로 옮기고 다른 활성 노드가 변경되지 않았음을 대조했다. 마지막 검증에서 휴지통의 루트 묶음 2개를 노드 3개와 비교해 assertion이 실패했으나, 읽기 전용 재확인에서 **노드 3개·삭제 상태 3개·루트 묶음 2개**를 확인했다. 추가 삭제·복구를 재실행하지 않았다. 실제 EDITOR 브라우저에서도 빈 공개 목록과 휴지통 API 권한 거절을 확인했다. 기존 업무일지는 유지했고 영구 삭제하지 않았다.

> Work는 운영자가 업무 문서를 관리하고 로그인한 회원에게 공개 문서를 제공하는 기능입니다. 운영자가 작성한 폴더·문서 이름, 폴더 구조, Markdown 본문, 공개 상태, 수정 버전, 작성·수정·삭제 시각과 작성자 내부 식별자를 서비스 데이터베이스에 저장합니다. MEMBER와 EDITOR는 문서와 상위 폴더가 모두 공개된 항목만 조회·검색·열람할 수 있습니다. 회원에게는 정제된 본문을 제공합니다. 새 항목과 휴지통에서 복구한 항목은 비공개로 시작합니다.

>

현재 검토 화면의 두 링크는 사용자가 직접 전송할 이메일 초안을 연다. 운영자가 본인과 범위를 확인한 뒤 전용 DB 작업을 수행하는 방식이다. `003_member_withdrawal.sql`은 스키마와 운영자 함수를 준비하고, `004_withdrawn_post_visibility.sql`은 댓글 보존과 본문 삭제를 추가한다. `005_withdrawal_upload_settlement.sql`은 보존할 공개 파일에서 계정 연결을 분리할 수 있게 한다. migration 적용은 기존 글·댓글·파일을 삭제하지 않는다. 운영 실행 전에 신규 앱 이미지와 해당 migration을 모두 적용한다.

1. 가입에 사용한 이메일로 접수하고, 본인 확인 뒤 대상 계정의 내부 ID와 선택을 확정한다. 비밀번호, OAuth 토큰과 인증 코드는 받지 않는다. Git 밖의 접근이 제한된 처리 기록에는 요청에 필요한 내부 ID·선택·상태와 완료 시각만 남긴다. 메일 발신자 주소만으로 본인 확인을 완료하지 않는다.
2. 아래 미리보기에서 계정 상태와 영향 건수를 확인한다. OWNER와 소유 R2 업로드가 있는 계정은 중단한다. `discussionPosts`는 본문이 지워져도 댓글 때문에 남기는 글 수다. 기존 글이 다른 작성자의 탈퇴로 익명화된 댓글을 가진 경우도 같은 규칙을 적용한다. 업로드 차단을 우회하기 위해 DB 행만 먼저 지우지 않는다.
3. `keep`은 공개 글·공개 글의 자기 댓글을 남겨 작성자 FK를 비우고 `탈퇴한 회원`으로 표시한다. `delete`는 대상자의 글과 댓글을 삭제한다. 두 선택 모두 삭제 대상 글이나 초안에 다른 작성자 댓글이 있으면 원문·렌더링 본문·요약과 작성자 연결을 비우고 글 제목·주소·공개 상태와 다른 작성자 댓글을 남긴다. 대상자 본인의 댓글은 삭제 범위에 따라 제거한다. 다른 글이 사용하는 카테고리는 이름·주소와 연결을 남기고 소유자만 비우며, 연결 글이 없는 대상자 카테고리는 삭제한다. 제목·주소·파일에 직접 넣은 개인정보는 별도 검토한다.
4. 처리 가능하면 승인된 작업 시간에 앱 요청을 차단하고 확인된 백업을 준비한다. DB 작업을 실행한 뒤 세션과 Google 연결 행의 제거, 공개 화면과 API에 이전 이름·ID가 없는지 확인한다. 기존 계정 로그인과 작업이 겹치지 않게 앱을 중단하고, 서비스 재개 전 앱의 ISR 산출물과 관련 공개 응답의 캐시를 확인한다. 이후 Google 로그인하면 새 MEMBER 계정으로 가입될 수 있으며 이전 작성물 소유권은 복원되지 않는다.
5. 업로드 때문에 차단되면 아래 조회로 공개/비공개 객체, 다른 글·댓글·About에서 공유 중인 참조, 업로드 예약과 서명 URL 만료 시각, CDN 캐시를 분류한다. 각 업로드의 유지·삭제 범위를 확인하고 DB 처리를 마친 뒤 탈퇴 미리보기를 다시 실행한다.
6. 과거 백업을 복원할 때는 격리 상태에서 해당 앱 버전의 migration과 권한을 적용한다. 백업 시점 이후 완료 기록의 정확한 회원 내부 ID·업로드 ID와 선택을 사용한다. 파일별 보존·삭제 결과를 먼저 다시 검증·반영한 뒤 회원 탈퇴를 재적용한다. `missing`은 그 내부 ID의 행이 이미 없거나 복원 시점에 존재하지 않았다는 뜻이므로 완료 기록 및 현재 상태와 대조한다. 같은 이메일로 새 계정을 찾아 적용하지 않는다. `blocked`를 해결하고 세션·공개 조회 상태를 확인한 뒤에만 트래픽을 연결한다. 재적용 기록의 보존 기간은 복구에 사용할 수 있는 백업 범위와 함께 확정한다.

유지된 콘텐츠는 게시물 API에서 `authorId: null`, `authorName: '탈퇴한 회원'`으로 반환한다. 기존 회원이 작성한 콘텐츠는 원래 형식을 유지한다. 소유자 없는 카테고리·콘텐츠는 OWNER가 관리하며 일반 편집자에게 권한을 넘기지 않는다.

OWNER는 `/manage?view=withdrawn`의 각 글에서 `비공개로 전환` 또는 `공개로 전환`을 선택한다. 본문 삭제 표시가 있는 글은 댓글을 보존하므로 일반 글 편집·삭제 기능에서 제외한다. 비공개 전환은 댓글을 포함한 공개 글 접근을 막고, 다시 공개하면 기존 다른 작성자 댓글이 돌아온다. 공개 범위를 바꾸기 전에 남아 있는 제목·주소와 댓글의 공개 적합성을 확인한다.

### DB 미리보기와 적용

먼저 격리 PostgreSQL에서 검증한다. 적용 권한은 스키마 소유 역할로 제한하고, 운영 앱·정리 작업에는 부여하지 않는다. 승인된 운영자 터미널의 `psql`에서 SQL 입력 이력과 파라미터 로그 설정을 확인한다. 내부 ID나 메일 주소를 Git과 공유 기록에 남기지 않는다.

```psql
\set ON_ERROR_STOP on
\set HISTFILE /dev/null
SET lock_timeout = '2s';
SET statement_timeout = '20s';
\prompt '확인된 회원 내부 ID: ' target_id
\prompt '회원이 고른 처리 방식 (keep/delete): ' content_choice
SELECT blog_schema.withdraw_member(:'target_id', :'content_choice');
```

결과가 `preview`이고 검토가 끝난 같은 대상과 선택에 한해 다음을 실행한다. 단일 호출이 하나의 트랜잭션으로 처리되며, 타임아웃·DB 오류 시 적용되지 않는다. 재시도 전 미리보기를 다시 실행한다.

```psql
SELECT blog_schema.withdraw_member(:'target_id', :'content_choice', true);
\unset target_id
\unset content_choice
```

`applied` 결과의 건수는 처리 전 영향 범위다. 운영 기록에는 확인된 종료 상태를 남긴다. `missing`과 `blocked`는 회원 데이터 변경을 뜻하지 않는다.

### R2 사전 조회

소유권을 확인한 회원의 내부 ID와 선택을 운영자 전용 터미널에서 입력한다. 승인된 DB 연결값은 보호된 실행 환경으로 공급한다. 데이터 네트워크 전용 실행에서는 DB 조회를 사용한다. `--r2`는 DB와 R2에 모두 접근 가능한 승인된 관리 환경에서 두 버킷에 한정된 별도 읽기 전용 키로만 실행한다.

```sh
node --import tsx scripts/inspect-withdrawal-uploads.ts keep
node --import tsx scripts/inspect-withdrawal-uploads.ts delete --r2
```

- 한 페이지에 최대 20개다. `next`가 있으면 그 값을 다음 조회에 입력한다. 내부 업로드 ID·상태·공개 구분·생존할 참조 건수만 출력한다. 비공개 결과를 공유 로그나 Git에 저장하지 않는다.
- `--r2`는 두 버킷의 권한을 확인한 뒤 비공개 `pending/<id>`와 DB 공개 구분에 맞는 `objects/<id>`에 HEAD를 보낸다. 준비·실패 상태에도 완료 객체가 존재할 수 있다. `expectedKey: false`이면 R2 조회를 건너뛰고 별도 확인 대상으로 둔다. 403·타임아웃은 부재로 계산하지 않는다. 한 페이지의 R2 조회는 최대 60초다.
- 글 원문·렌더링·남기는 메타데이터와 About의 JSON 항목, 댓글에서 업로드 ID를 찾는다. 결과가 0이어도 인코딩이 다른 URL, 외부 사이트, 이전 백업이나 브라우저 캐시의 참조가 남아 있을 수 있다. 삭제 결정 전 결과와 대상 콘텐츠를 비공개로 대조한다.
- 실제 정리 시 서명 URL 발급을 중단한 뒤 PUT 최대 300초와 GET 최대 60초의 남은 수명을 확인한다. 승인된 객체만 원본과 공개 캐시를 각각 확인한다. 원본 제거 뒤 공개 URL이 계속 응답하면 해당 파일만 purge하고 실제 공개 GET 결과를 확인한다. [R2 서명 URL](https://developers.cloudflare.com/r2/api/s3/presigned-urls/) · [Cloudflare 단일 파일 purge](https://developers.cloudflare.com/cache/how-to/purge-cache/purge-by-single-file/)

### 확인된 파일의 DB 처리

업로드 한 건씩 진행한다. 앱을 중지해 새 참조와 서명 URL 발급을 차단하고, 마지막 발급 이후 5분 이상 대기한다. DB의 예약 시각도 확인하되, 이 시각만으로 최근 다운로드 서명이 만료됐다고 판단하지 않는다. 초기 조회 결과와 대상 콘텐츠를 대조해 회원이 선택한 범위를 확정한다. 처리 완료 기록에는 내부 회원 ID·업로드 ID·탈퇴 선택·파일 처리 유형과 확인 시각만 제한된 곳에 남긴다.

| 유형 | 확인 조건 | 적용 결과 |
| --- | --- | --- |
| `retain-public` | 남을 글·댓글·About에서 참조하는 `PUBLIC/READY` 행. 비공개 버킷 임시·완료 경로는 부재. 공개 버킷 완료 객체는 존재하고 정확한 공개 URL의 GET은 200. | 공개 파일과 주소를 보존하고 회원 FK를 분리한다. |
| `removed` | 남을 참조가 없고 비공개 임시·비공개 완료·공개 완료 세 경로에 객체가 없음. 공개 유형이면 정확한 공개 URL의 GET도 404. | 외부 정리가 검증된 해당 회원의 업로드 행 한 건을 제거한다. |

DB와 R2에 접근할 수 있는 운영자 전용 환경에서 실행한다. 스키마 소유 역할의 `DATABASE_URL`과 대상 두 버킷에 한정된 R2 읽기 권한은 보호된 환경 변수로 공급한다. 이 도구의 R2 작업은 HEAD와 공개 GET이며, 원본 삭제와 purge는 승인된 별도 절차로 먼저 수행한다. 공개 GET은 리디렉션을 따라가지 않고 캐시 우회용 쿼리를 붙이지 않는다. 비공개 업로드 ID를 공개 주소로 요청하지 않는다.

```sh
node --import tsx scripts/settle-withdrawal-upload.ts delete retain-public
node --import tsx scripts/settle-withdrawal-upload.ts delete removed
```

첫 인자는 회원이 고른 `keep` 또는 `delete`다. 미리보기에서 `verified: true`를 확인한 경우에만 같은 명령에 `--apply`를 붙여 실행한다. 유형과 정확한 업로드 ID를 입력해 확인하면 도구가 R2와 공개 응답을 다시 검사한다. 이어 짧은 DB 트랜잭션에서 소유권·상태·참조를 다시 확인한다. 충돌 또는 `changed`이면 변경 없이 멈추므로 미리보기부터 다시 시작한다. `missing`이면 완료 기록과 현재 행을 대조한다. 운영 회원의 실제 파일 정리 및 운영 DB 적용은 격리 검증과 구분한다.

## MEMBER·EDITOR 운영 인수 순서

- 동의한 OWNER 외 Google 계정의 최초 로그인과 MEMBER 역할을 확인한다. 승인된 공개 검증 글에서 댓글 작성과 자기 댓글 삭제를 검증한다. 타인 댓글 삭제, 글 작성, 회원 역할 변경은 서버에서 거절되는지 확인한다. 공개 검증 글이 없으면 댓글 검증은 보류한다.
- OWNER가 승인한 계정을 EDITOR로 변경한다. 같은 세션에서 서버 역할 갱신과 자기 글 초안 작성·수정을 확인한다. 타인 글 수정·타인 초안 조회·About 편집·회원 권한 관리는 서버에서 거절되는지 확인한다. 다른 작성자의 비공개 글과 검증용 ID는 공유 기록에 남기지 않는다.
- 인수가 끝나면 승인된 계정 상태와 검증 콘텐츠 처리 여부를 기록한다. 이번 검토에서 회원 생성·댓글 작성·권한 변경은 수행하지 않았다.

## 확인 결과

- 2026-11-04 실제 R2와 CDN에 합성 검증 파일을 사용했다. Cloudflare에서 계정과 두 버킷 및 공개 도메인 활성 상태를 확인하고, 로컬 환경 파일을 수정하지 않은 채 검증 프로세스에서만 확인된 버킷·HTTPS 주소를 사용했다. 공개 PNG의 원본 바이트와 `MISS → HIT`, 임시 객체가 남을 때 보존 처리 거절, 비공개 완료 객체 삭제 전·후 결과를 확인했다.
- 검증 PNG 원본 삭제 뒤에도 정확한 공개 URL이 200을 반환해 `removed` 검증이 거절됐다. 이번에 생성한 URL 한 건만 purge하자 정확한 공개 GET 404와 R2 세 경로 부재, `verified: true`가 확인됐다. 생성 시 부재 조건을 사용하고 생성 표식이 일치하는 검증 객체만 정리했다. 기존 운영 파일, 운영 DB, CDN 설정은 건드리지 않았다. [R2 S3 API](https://developers.cloudflare.com/r2/api/s3/api/) · [Cloudflare 단일 파일 purge](https://developers.cloudflare.com/cache/how-to/purge-cache/purge-by-single-file/)
- 로컬 격리 PostgreSQL 16의 실제 migration 001~005에서 런타임 권한·잠금·새 참조 차단을 확인했다. 삭제한 검증 PNG의 실제 R2/CDN 확인 결과를 이용해 정확한 합성 업로드 행만 제거했고, 공유 행의 회원 연결 분리와 세션 제거·탈퇴까지 검증했다. `pg_dump`/`pg_restore` 후 같은 처리를 재적용했다. 운영 PostgreSQL 접속과 배포는 대기다.
- 파일 처리 도구는 모의 S3·CDN에서 임시·완료 객체가 남거나 공개 캐시가 응답할 때 차단함을 확인했다. 로컬 PostgreSQL 18.4의 실제 잠금 충돌과 새 참조 차단, 처리 후 회원 탈퇴, PGlite 백업 복원 후 파일 처리·탈퇴 재적용을 확인했다. 실제 운영 R2·CDN의 원본 삭제와 purge는 아직 실행하지 않았다.
- PostgreSQL 18.4의 격리 환경에서 `003` 적용 DB를 `004`로 올려 기존 글·댓글과 함수 실행 권한이 유지됨을 확인했다. 탈퇴와 동시에 등록 중이던 다른 회원의 댓글을 보존하고 `pg_dump`/`pg_restore`로 복원 후 같은 선택을 재적용했다. 운영 PostgreSQL 16과 운영 R2·CDN은 별도 인수가 필요하다.
- 업로드 사전 조회는 격리 DB의 유지·삭제 선택별 참조 결과, 모의 S3의 두 버킷 및 임시·완료 객체 조회, 접근 거절과 객체 부재 구분을 확인했다.
- 탈퇴 함수의 유지·삭제, OWNER·소유 업로드·연쇄 댓글 삭제 차단, runtime 실행 거절, 세션·Google 연결 제거, 이전 백업 복원 후 두 선택의 재적용을 격리 PGlite에서 검증했다. 타입·경계·테스트 9개·빌드와 실제 migration을 사용한 standalone E2E 5개가 통과했다.

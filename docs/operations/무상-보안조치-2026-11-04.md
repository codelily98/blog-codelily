## 백업과 복구

서버의 `codelily-backup.timer`는 매일 03:00 이후 5분 분산으로 실행하고 완성된 백업을 7일 유지한다. 실패한 `.partial` 백업은 완성본으로 취급하지 않는다. 백업마다 암호문 크기·SHA256 manifest를 만든다. 백업 스트림·해시 계산은 메모리 사용량을 제한하며 평문 DB·운영 설정을 파일로 저장하지 않는다.

PC의 `Codelily-Encrypted-Backup-Pull` 작업은 매일 09:00 및 해당 사용자 로그온 때 실행한다. 백업 계정에는 sudo·Docker 그룹 권한이 없고, SSH 강제 명령으로 암호화 snapshot만 내보낸다. 포트 전달·PTY·임의 shell 명령은 허용하지 않는다. PC에서는 tar 경로와 허용 파일명을 검증한 뒤 크기·SHA256을 확인하며 7일 보관한다. 예약 작업의 실제 종료 코드 0을 확인했다. PC가 꺼져 있거나 로그인되지 않은 동안에는 외부 사본이 갱신되지 않는다. 한 번의 암호문 수신은 최대 512MiB로 제한한다.

최초 암호화 DB를 **네트워크·host port·영속 volume이 없는 별도 PostgreSQL**에 복호화/복원하고, 모든 blog_schema 테이블 건수를 운영 원본과 비교해 일치를 확인했다. roles/configuration/Caddy 자료도 복호화해 읽을 수 있음을 확인했다. 테스트 컨테이너는 제거했다. 이후 최종 설정을 포함한 백업과 외부 사본의 해시도 재검증했다. roles의 암호/권한을 포함한 완전한 신규 호스트 재구축 연습과 R2 객체의 별도 백업은 이 검증에 포함하지 않는다.

복구 비밀키와 기존 SSH 개인키의 독립된 오프라인 사본은 사용자가 별도로 안전하게 보관해야 한다. 서버에는 복구 비밀키를 남기지 않는다. PC와 키를 함께 잃으면 외부 암호문만으로 복구할 수 없다.

복원은 운영 DB가 아닌 격리 DB부터 수행한다. 예를 들어 사용자 비공개 경로의 identity를 사용해 `age -d -i <identity> <database.dump.age>`의 출력을 `pg_restore --exit-on-error --no-owner --no-privileges`로 전달한다. roles/권한, 운영 설정, 원본 TLS, 파일 참조는 별도로 확인한다. 운영에 적용하기 전 복구 시점과 현재 쓰기 중단 범위를 검토한다.

## 운영 파일과 재설치

- `infra/security/`: SSH·APT·journal·systemd service/timer 템플릿.
- `scripts/operations/harden-host.py`: **별도 ubuntu 키 접속/sudo 검증 후** root로 실행한다. `--ssh-source <관리 IPv4>`를 반복하고, 기본 검토 후에만 `--apply`를 사용한다. 10분 복구 timer를 만들며 새 접속 성공 후 `codelily-security-rollback.timer`를 취소해야 한다. 현재 적용된 snapshot이 있으면 재적용을 거절한다.
- `scripts/operations/install-backup.sh <공개 recipient 파일> <백업 전용 SSH 공개키 파일>`: age가 설치된 서버에서 백업 export 계정/강제 명령/타이머를 구성한다. 공개키 입력도 Git 밖에서 전달한다. `backup.py`는 운영 서버 checkout의 고정 서비스 이름/경로를 사용한다.
- `scripts/operations/backup.py`: root 실행. 정상 일일 백업은 private identity가 필요 없다. `--verify-with-identity <비공개 경로>`는 격리 복원 연습용이며 테스트 뒤 서버의 임시 identity를 제거한다.
- `scripts/operations/pull-backups.ps1`, `register-backup-task.ps1`: PC의 `.local/secrets/backup-export`와 SSH 별칭을 사용한다. 결과는 `.local/backups/`와 `last-success.json`에만 둔다. 해당 경로들은 Git 제외다.
- `infra/cloudflare/security-rules.json`: 현재 무료 규칙의 재현 가능한 본문. 기존 ruleset을 먼저 조회하고 타인 변경을 덮어쓰지 않는다. 규칙 ID·API 인증·개인 IP는 이 파일에 넣지 않는다.

새 PC·서버 작업은 `ssh iwinv-cloud`의 ubuntu 접속을 기본으로 한다. 관리 명령은 `sudo`로 실행한다. VS Code가 과거 `/root` 폴더를 열어 `chdir(2) Permission denied`를 표시하면 `/home/ubuntu` 또는 읽기 가능한 `/opt/codelily`로 새 창을 연다. `/root` 권한을 완화하지 않는다. 서버에서 앱을 빌드하지 않는다.

## 무료 WAF의 범위와 rollback

Free 속도 제한은 Host/Method 조건을 직접 사용할 수 없으므로 custom 규칙에서 **다른 hostname 또는 GET/HEAD/OPTIONS만 `http_ratelimit` phase를 건너뛰게** 했다. 관리형 WAF·DDoS·다른 custom 규칙은 건너뛰지 않는다. 실제 제한은 blog 쓰기에만 적용된다. Google callback·R2 직접 PUT·공개 조회는 포함하지 않는다. 추후 같은 zone의 다른 앱에 속도 제한을 추가할 때 이 scope guard도 함께 재설계해야 한다.

두 custom block은 blog 호스트로 한정한다. 무료 rule 전체 본문을 dry-run 검증하고 scope guard → rate 순서로 반영했다. 긴급 rollback은 `codelily_write_rate`만 먼저 비활성화한다. scope guard를 먼저 없애면 다른 호스트까지 새 rate 규칙의 영향을 받을 수 있다. 두 block은 별도로 비활성화할 수 있다.

서버 SSH/호스트 방화벽의 적용 전 파일은 root 전용 rollback snapshot에 남겼다. 정책 복원은 콘솔/검증된 관리자 세션에서 검토 후 수행한다. 원본 Compose/Caddy도 별도 비공개 snapshot에 보관한다. HSTS는 브라우저에 최대 1일 남으므로 헤더 제거만으로 즉시 소급 취소되지 않는다.

## 검증과 작업 중 문제

- 신규 ubuntu SSH·sudo 성공, root 신규 SSH 거절, 사용자 본인 기존 키 접속도 확인. 기존 키 서명이 자동 환경에서 안 돼 사용자 승인으로 만료형 임시 키를 사용했다. 마무리 때 root/ubuntu의 임시 등록을 제거하고 해당 키의 신규 접속 거절을 확인했다. PC 임시 개인키·공개키도 제거했다. 기존 소유자 키와 제한된 백업 전용 키는 유지한다.
- 80·443·3000·5432·6379·2375·2376 직접 연결은 시간 초과, 관리 PC의 22만 연결 성공. 모든 인터넷 source/UDP 검증을 의미하지 않는다.
- 재부팅 후 앱/DB/Redis healthy, Caddy/Tunnel 실행·새 컨테이너 재시작 0, NTP 동기화, 실패 systemd unit 0. 원본 인증서 검증/readiness·백업·maintenance 모두 exit 0.
- public posts/readiness/API 200, 개인 API private/no-store, 내부 API 404. 비밀 경로는 새 WAF에서 403이다. 익명 업로드 요청 90회(약 4.7초, 여러 colo)에 401 89회·429 1회를 관측했고 파일/게시글/계정은 생성하지 않았다. 이 임계값은 전역 요청의 정확한 60번째 차단을 보장하지 않는다.
- 개발 PC 공개 페이지 및 naraebi 200, 서버 자체 공개 요청도 SIN 200을 확인했다. 이전 SJC 장애의 원인을 이번 조치로 확정하지 않는다.
- 공개 브라우저 새로고침에서 제목/글 목록과 console error/warning 0을 확인했다. 앱 UI 변경이 없어 이번에는 desktop/mobile 전체 접근성 회귀를 반복하지 않았다. 실제 Google 왕복·에디터 업로드는 계속 별도 인수다.
- 타입·모듈 경계·테스트 7개·프로덕션 빌드 통과. 첫 로컬 빌드는 sandbox `.next` mkdir EPERM, 같은 빌드의 권한 조정 재실행은 성공했다. Python 구문·서버 systemd/Compose/Caddy 문법·실제 서비스 실행·PC 작업 스케줄러도 검증했다.
- Caddy의 file capability 요구를 놓치고 cap ALL 제거만 적용해 일시적으로 exit 126/502가 발생했다. `NET_BIND_SERVICE` 하나를 허용해 즉시 복구했고, 원본 TLS·공개 응답·백업 성공을 재확인했다. 정상 동작 검증 전 상태를 완료로 기록하지 않았다.
- iwinv 편집 fragment에 직접 접근했을 때 JS/CSS가 없어 편집할 수 없었고, 정상 부모 페이지의 modal로 반영했다. 저장 버튼 표시가 오래 남아 별도 조회에서 실제 22/TCP 두 규칙만 남았음을 확인했다.
- 초기 보존 작업의 자동 승인 검토 거절 후 삭제 없이 대상 0건만 조회했다. 사용자가 보존 조건을 명시 승인한 뒤에만 실제 실행/예약했다.

## 다음 작업·한계

Google 최초 OWNER 로그인·로그아웃과 실제 에디터 이미지 업로드를 진행한다. 실제 크기 불일치/동시 변경 경합, 월간 복원 연습, 인증서 자동 갱신의 장기 관측, R2 lifecycle·독립 객체 백업, 외부 장애 알림, 앱/고정 이미지 CVE 전수 검사는 별도다. CSP와 컨테이너 read-only rootfs는 OAuth/에디터·쓰기 경로 호환성 검증 후 확장한다. 이번 무상 보안 조치가 침해 없음이나 전체 보안 인증을 뜻하지 않는다.

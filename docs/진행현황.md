# Codelily 진행현황

최종 갱신: 2026-11-03 (Asia/Seoul)

## 2026-11-03 운영 배포 준비

- 사용자 확인: iwinv Ubuntu 26 LTS 서버 구매, SSH inbound는 개발 PC만 허용, HTTP/HTTPS 및 outbound 방화벽 설정. 실제 OS·규칙은 서버 접속 후 검증한다. 가비아 도메인 등록과 Cloudflare 네임서버 위임은 완료됐으며 기존 `naraebi.codelily.kr`을 유지한다.
- 신규 `blog.codelily.kr` 전용 Tunnel·host별 보안/캐시 규칙과 outbound DNS 53/TCP·UDP 및 Tunnel 7844/TCP·UDP 확인을 [최초 배포 실행서](operations/iwinv-최초배포.md)에 작성했다. Node.js는 앱 이미지에 포함하고 Redis는 실제 사용 전까지 선택 profile로 유지한다.
- 운영 Compose에 신규 DB runtime/migrator/maintenance 초기화, post-migration 최소 권한 SQL, Redis 인증 healthcheck를 추가했다. `scripts/setup-production.mjs`는 기존 비밀값을 보존하며 새 env/secret을 만들고 값은 출력하지 않는다. Docker build context에서도 `.env`를 제외했다.
- 검증: 테스트 5개·모듈 경계·타입 검사 통과. 별도 실제 PostgreSQL 16/Redis에서 초기화·migration·healthcheck·runtime DDL/이력 쓰기 차단·maintenance의 회원/게시물 접근 차단 통과. Linux non-root 설정 생성과 디렉터리/secret/env의 0700/0444/0600 권한 통과. 임시 검증 컨테이너·볼륨은 정리했고 기존 개발 컨테이너는 유지했다.
- Windows 빌드는 기본 sandbox에서 산출물 생성 EPERM으로 실패했으나 동일 명령을 권한 조정 후 재실행하여 통과했다. 이번 변경에는 렌더링 UI 변경이 없으므로 브라우저 E2E는 재실행하지 않았다. 이전 E2E 5개 결과는 2026-11-02 기록이다.
- SSH 키 인증 완료. 실제 Ubuntu 26.04 LTS/amd64·2 CPU·약 8GB RAM 및 기존 웹/DB 서비스가 없는 신규 서버임을 확인했다. Docker 공식 APT 저장소로 Engine 29.9.2/Compose 5.7.0을 설치하고 hello-world를 실행했다. Node 24·고정 PostgreSQL16/Redis7·cloudflared 2026.10.7 이미지를 pull했다.
- Ubuntu 기본 chrony NTS의 4460/TCP가 시간 초과되어 동기화되지 않았다. 사용자가 ELCAP outbound 4460/TCP를 허용한 뒤 chrony를 재시작해 `NTPSynchronized=yes`, 정상 Leap 상태를 확인했다. 호스트 UFW는 없으며 iwinv 방화벽 규칙 원본은 별도 관리한다.
- 원격 저장소를 신규 배포 경로에 clone했다. 서버 접속 정보·개인키 경로·비밀값은 문서화하지 않는다. DNS·Cloudflare 계정에는 아직 변경하지 않았다.
- 운영 secret/env를 서버에서 생성했다. 개발 PC에서 앱·migrator·Caddy 2.11.7/Cloudflare DNS module v0.2.4 이미지를 빌드하고 SSH로 전송해 archive SHA-256과 image ID를 검증했다. 최초 배포는 registry 발행 없이 save/SCP/load 방식이며 [이미지 명세](../infra/releases/2026-11-03-bootstrap.json)에 버전을 기록한다. 호스트 유실 복구를 위해 검증 이미지의 외부 보관/registry 발행은 후속 과제다.
- 실제 서버의 `code-lily`·PostgreSQL·Redis 3개 컨테이너 healthy, migration·최소 권한 SQL·maintenance 실행 및 readiness 200 확인. `/posts`·`/about`·`/api/posts`도 200이고 공개 ISR 300초·개인 API no-store 헤더를 확인했다. 호스트에는 SSH와 시스템 DNS 등만 listen하며 앱/DB/Redis 공개 포트가 없다. 개발 seed는 운영에서 실행하지 않았다.
- 관측 시점 idle 메모리: 앱 약 65.8MiB/512MiB, DB 약 41.3MiB/1536MiB, Redis 약 3.5MiB/256MiB. 부하 측정이나 운영 용량 보장은 아니다.
- Caddy 설정은 더미 token을 사용한 validation을 통과했으며 실제 인증서는 아직 발급하지 않았다. `scripts/configure-cloudflare-secrets.sh`를 서버에 준비했고 token은 대화형 숨김 입력으로만 받는다. Tunnel outbound 7844/TCP 도달을 확인했으나 실제 Tunnel 인증/QUIC/원본 TLS는 미검증이다.
- 비밀 입력 도구는 실 token과 분리한 임시 디렉터리/가상 터미널에서 Bash 구문·비대화형 차단·입력값 비출력·원자적 저장·0444 권한을 검증했다. DNS API token 형식도 저장 전 확인한다.
- 다음 순서: 실제 Cloudflare token 등록 → Caddy 인증서 → 신규 Tunnel/hostname → Google/R2 및 백업 인수. 운영 인수 미완료이며 공개 배포 성공으로 표시하지 않는다.

- 추가 동기화: 개발 서버가 생성한 `apps/code-lily/next-env.d.ts`의 `.next/dev/types` 참조를 반영했다. `npm run typecheck`와 `git diff --check`를 통과했다. 기능 변경은 없으며 외부 연동 대기 항목과 다음 시작점은 아래와 같다.

## 확정 사항

- 운영: iwinv Gen2 Dedicated `hpa_2.8-g2`, 2 vCPU / 8GB / NVMe 100GB, 30GB/일(월 1,000GB), 표시 월 48,200원(공식 표기 부가세 별도).
- 도메인: `blog.codelily.kr`. 최초 관리자 Google 이메일: `codelily98@gmail.com`. DB 권한의 최종 근거는 사용자 역할이며 초기 관리자만 검증된 이메일 allowlist로 지정한다.
- Next.js 풀스택, NestJS식 기능 모듈·계층 분리. 별도 NestJS 프로세스는 초기 도입하지 않는다.
- 라이트·다크, 반응형, KWCAG 2.2와 WA 심사 기준 지향. 인증 획득은 별도 심사 대상이다.
- Caddy + Cloudflare Full (strict), DNS-01 자동 인증서 발급·갱신. Cloudflare CDN 적극 활용.
- 파일: Cloudflare R2, 공통 S3 API adapter, 공개 CDN 객체와 개인 파일 bucket 분리.
- SunEditor, react-chartjs-2, Tabulator Grid는 공유 React wrapper로만 사용한다.

## 이번 작업 기록

- 기존 4GB/6앱 예제는 과거 검토 자료로 보존한다. 현재 구현 기준은 `architecture/결정기록.md` 및 `infra/`다.
- 루트 AGENTS와 프로젝트별 재개 문서를 작성했다.
- 사용자 지시에 따라 로컬 Docker Desktop `desktop-linux`의 기존 컨테이너 5개·볼륨 4개·이미지 6개를 초기화했다. 재사용 가능한 setup에 전역 삭제 명령을 넣지 않았다.
- Root `compose.yaml`로 PostgreSQL 16·Redis를 새로 만들고, 실제 migration/runtime 역할 분리·DDL/교차 스키마 차단·migration 이력 쓰기 차단·Redis ACL을 확인했다.
- 운영 `infra/compose.production.yml`에 app·DB·Caddy·Tunnel과 `tools` profile의 migration/maintenance를 분리했다. 공개 host port는 없다.
- Windows standalone 빌드·Linux Docker 이미지 빌드, 타입/모듈 경계, 단위·SQL 통합 4개, 실제 Chrome E2E 5개 통과. Docker DB에서 실제 게시물 DML도 검증했다.
- E2E는 격리된 서명 세션과 임베디드 PostgreSQL wire fixture를 사용한다. 실제 Google provider 인증은 하지 않았으며 운영 계정으로 위장하는 route를 만들지 않았다.
- E2E 환경 `http://localhost:3000`, desktop 1440×1100 / mobile 390×844, Browser 플러그인 미설치로 Playwright Chrome 사용. 공개 페이지·편집기·관리 Chart/Grid의 자동 접근성 검사와 검색 모달 초점·Escape 복귀 통과.
- `x-nextjs-cache: HIT`, `s-maxage=300`, 글 공개 해제 후 404를 실제 standalone 응답으로 확인했다.
- 첨부 원본/생성 콘셉트/브라우저 screenshot의 팔레트·header·sidebar·카드·타이포·About·모바일 구조를 비교했다. brand/콘텐츠·터치 영역·보조 글자 대비·모바일 2줄 header는 의도적 변경이다.
- 초기 예시 글 6개와 About을 제공했다. 실제 개인 이력·프로필·공개 연락처로 교체한 뒤 운영한다.


## 다음 작업 시작점

1. Root AGENTS → 작업 시작 → code-lily 문서를 읽는다.
2. `docker compose --profile web ps`로 로컬 상태를 확인하고 필요 시 `npm run local:up`으로 앱을 실행한다.
3. 외부 Google/R2 설정을 비공개 환경 파일에 반영하고 실제 인증·파일 경로를 검증한다.
4. Cloudflare Tunnel/WAF/Caddy와 운영 DB·백업을 적용한다. 자동 검사 통과를 WA 인증 획득으로 표현하지 않는다.
5. 후속 `admin-dashboard`, `resume-site`, `intro-page`는 설계/체크리스트 상태이며 아직 독립 앱으로 구현하지 않았다.

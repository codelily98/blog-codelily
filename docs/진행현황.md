# Codelily 진행현황

최종 갱신: 2026-11-03 (Asia/Seoul)

## 2026-11-03 R2 실전송·운영 반영

- 사용자가 private CORS·공개 custom domain Active·최소 권한 S3 키 등록을 완료했다. `dde7621` 소스의 검증된 앱 이미지를 활성화했으며 운영 R2 환경 6개 반영과 readiness 200을 확인했다. [활성화 명세](../infra/releases/2026-11-03-r2-active.json)를 현재 상태로 사용한다. 아래 준비 기록은 당시 이력이다.
- 실제 두 버킷 접근, 허용 Origin PUT preflight, 서명 업로드, HEAD/파일 서명/ETag 검증, 공개 버킷 복사·이미지 내용 일치, 60초 서명 비공개 PDF 다운로드·no-store, 서명 없는 S3 요청 거부, 위장 이미지 거절을 통과했다. 테스트는 운영 회원/게시글을 만들지 않고 생성한 UUID 객체만 정리했다.
- R2는 서명 없는 S3 요청에 400/InvalidArgument를 반환했다. 유효한 서명 요청의 200·동일 바이트 확인과 함께 접근 거부로 판정하도록 진단 도구를 보완했다. 도구에는 비허용 Origin 확인과 파일 형식 거절 이유 확인도 추가했다. 이 두 강화 조건은 strict 타입 검사만 통과했고 실계정 재실행은 다음 CDN 검증 때 수행한다.
- 공개 R2 응답은 HTTPS 200·image/png·`public, max-age=31536000, immutable`이지만 반복 응답은 아직 DYNAMIC이다. 사용자가 Cache Rule을 설정 중이며 전체 URI 와일드카드 값에는 `https://public-blog-r2.codelily.kr/objects/*`만 넣도록 안내했다. 에지 TTL은 원본 헤더 사용/없으면 bypass, 브라우저 TTL은 원본 존중이다.
- 앱 교체 후 개발 PC에서 Posts/About/readiness/API 200, 공개 ISR 300초·개인 API private/no-store를 확인했다. Google 실제 로그인/에디터 업로드, SJC 블로그 502, WAF·외부 백업·갱신 관측은 별도 미완료다.
- 다음 시작점: Cache Rule 배포 확인 → 최신 `scripts/verify-r2.ts`를 검증용 migrator에 read-only mount해 `R2_VERIFY_WRITE=1 R2_VERIFY_CDN=1` 실검증 → HIT·강화 조건 결과 기록 → Google OAuth 인수. runtime 이미지는 이미 활성화했으므로 다시 교체하지 않는다.
- 도구 수정 후 앱 타입 검사·도구 단독 strict 검사(Bundler 해석/node types)·모듈 경계·테스트 7개·diff 공백 검사를 통과했다. 첫 단독 검사는 프로젝트와 다른 NodeNext/기본 types 옵션으로 실패해 올바른 CLI 옵션으로 재검증했다. runtime 코드/UI 변경이 없어 앱 이미지 빌드·브라우저 검사는 반복하지 않았다.

## 2026-11-03 R2 연동 준비

- 입력 도구 후속 수정: 사용자가 정상 공개 도메인 입력 직후 일반 오류로 종료됨을 보고했다. 실제 운영 R2 값은 저장되지 않은 상태(0개)를 확인했고 도메인 자체는 유효하다. 이전 도구가 메타데이터 전체를 나중에 검증해 앞선 입력 오류를 구분하지 못했던 점을 보완했다. 항목별 즉시 재입력·값 없는 구체적 오류·기존 Cloudflare account ID 기본값을 추가했다. Python 회귀 테스트 6개와 가상 터미널의 숨김 입력/설정 보존/0600 테스트를 통과했다. 당시 실제 입력값은 보관하지 않아 어느 앞선 값이 원인이었는지는 확정하지 않는다.
- 이번 수정은 호스트 입력 CLI뿐이며 앱/SDK/배포 이미지는 변경하지 않았다. 키 등록 후 실전송 검증과 staged 이미지 활성화는 계속 대기다.

- 사용자 확인 리소스: 비공개 `blog-storage`, 공개 `public-blog-storage`, 공개 custom domain `public-blog-r2.codelily.kr`. 최초 `blog-r2.codelily.kr`는 버킷 이름이 아니라 도메인이었으며 현재 공개 base URL에는 사용하지 않는다. 실제 S3 키·CORS·도메인 API 인수는 아직 대기다.
- [R2 설정 절차](operations/R2-연동.md)와 private CORS JSON, 숨김 입력 `scripts/configure-r2.py`를 준비했다. env 원자적 갱신/0600 backup·기존 앱 설정 보존·기존 R2 값 덮어쓰기 거부·비대화형 차단을 서버의 임시 환경에서 검증했다. 실제 운영 env는 아직 변경하지 않았다.
- 공통 storage에서 SDK가 본문 없는 presign 시 빈 파일 CRC32를 서명하던 문제를 재현해 `WHEN_REQUIRED`로 보완했고 Content-Type/Length를 서명에 고정했다. 버킷 이름에 도메인을 쓰거나 public/private를 같은 버킷으로 설정하는 경우도 거절한다. 테스트 7개·타입·경계 검사가 통과했으며 운영 이미지 반영은 다음 단계다.
- 공개 key `objects/<uuid>`는 확장자가 없으므로 custom domain 연결만으로 CDN HIT를 가정하지 않는다. **public-blog-r2 hostname의 objects GET/HEAD만** 캐시 적격성을 부여하고 원본 Cache-Control을 존중하는 규칙을 문서화했다. 비공개 bucket/서명 URL/블로그 HTML은 포함하지 않는다.
- 다음: CORS·최소 권한 S3 키 등록 → 수정 이미지 빌드/배포 → 실제 PUT/완료/비공개 GET·공개 CDN HIT 검증. Google OAuth 후 실제 에디터 이미지 삽입은 별도 인수다.
- 실계정 fixture 검증 CLI를 준비했고 별도 strict 타입 검사까지 통과했다. S3 제어 요청 timeout/재시도 상한을 추가했으며 테스트 7개·앱 타입·경계 검사를 다시 통과했다. 아직 실계정 성공 결과는 아니며 키 등록 후 수행한다.
- 최종 요청 중단 옵션을 포함한 `dde7621` 소스로 Linux 앱·migrator 빌드/타입 검증을 통과했고 archive hash·image ID 확인 후 서버에 로드했다. [대기 중인 이미지 명세](../infra/releases/2026-11-03-r2-staged.json)에 기록했으며 실행 앱/운영 이미지 변수는 아직 교체하지 않았다. 이전 `3efcda7` 이미지는 중간 준비본이고 실제 반영 대상은 `dde7621`이다.
- 공개 `public-blog-r2.codelily.kr`는 개발 PC에서 TLS 연결 및 없는 객체의 404를 확인했다. CORS 저장/도메인 Active와 최소 권한 S3 키의 서버 등록을 사용자에게 요청한 상태다. 다음 세션은 이 두 항목을 확인한 뒤 staged migrator로 `R2_VERIFY_WRITE=1` 실검증, 캐시 규칙/실제 HIT, 앱 이미지 교체 순서로 이어간다. 아직 R2 실제 전송 완료가 아니다.

## 2026-11-03 Cloudflare 연결 검증

- 최신 공개 경로: 사용자가 hostname 경로를 저장했고 API에서 `blog` CNAME이 실행 중인 신규 Tunnel을 가리키며 proxy ON임을 확인했다. `naraebi` DNS는 baseline과 동일하고 HTTPS 200이다.
- 개발 PC/HKG 경로에서 공개 Posts/About HTTPS 200, 원본 ISR HIT·s-maxage=300, 해시 CSS `CF-Cache-Status: HIT`·immutable 1년을 확인했다. 개인 API는 쿠키 유무와 관계없이 private/no-store·CF DYNAMIC, 내부 API는 공개 404다.
- 비용 절감 구성 재확인: 운영 컨테이너의 R2 환경변수 6개(account/key/secret/public bucket/private bucket/base URL)는 모두 미등록이다. R2 adapter 구현은 완료됐지만 실 파일 전송은 미연동이다. 공개 CSS CDN HIT와 private API no-store는 다시 확인했으며, 공개 HTML은 Cloudflare DYNAMIC + Next ISR 300초(관측 시 STALE 재검증) 정책이다. 다음 파일 단계는 실제 R2 bucket·권한 제한 key·CORS·media custom domain 등록 및 서명 업로드/검증/CDN 다운로드 인수다.
- 운영 도메인 Chrome/Playwright(브라우저 플러그인 미제공) 검증 통과: 1440×1100/390×844, 페이지 제목·비어 있지 않은 화면·오류 overlay 없음·console error/warning 0건, 검색 초점/Escape 복귀, 라이트 테마/새로고침 유지, About 이동, 가로 잘림 없음, 방문 기록 거부, 익명 쓰기 401·교차 Origin 403. 4개 화면 상태의 axe 자동 위반 0건이다. 이는 WA 인증 검증 전체를 의미하지 않는다. 운영 seed는 실행하지 않아 게시글 0개가 정상이며 원격 계정 OAuth는 아직 미구성이다.
- **미해결:** 서버 자체 공개 요청은 SJC 경로에서 502다. 같은 hostname/IP의 개발 PC/HKG 응답은 200이며, 서버 502 전후 Tunnel 요청 수는 증가하지 않고 connector 오류는 0이다. HTTP 버전·압축·User-Agent 비교와 connector 1회 재등록 후에도 지속됐다. 원본에 도달하기 전 경로 문제로 의심되지만 원인은 확정하지 않았다. [진단 기록](operations/Cloudflare-502-진단.md)을 이어서 확인한다. 전체 지역 운영 인수 완료로 표시하지 않는다.
- 추가 대시보드 확인은 Windows Computer Use가 현재 브라우저 URL을 충분히 확신할 수 없어 정책을 적용할 수 없다는 사유로 중단했다. 추가 UI 입력을 하지 않았으며 보안 검증이나 WAF를 해제하지 않았다.

- 사용자가 등록한 DNS token의 active 상태·zone 접근 권한과 Tunnel token의 계정 일치를 서버 내부에서 확인했다. 신규 Tunnel은 기존 `naraebi` Tunnel과 다르며, 기존 DNS는 변경 전 비공개 baseline으로 보관했다. 비밀값은 출력하거나 Git에 넣지 않았다.
- Caddy DNS-01로 `blog.codelily.kr`의 실제 Let's Encrypt 인증서를 발급했다. 원본 TLS 1.3에서 신뢰 체인·hostname 검증 성공, HTTPS readiness 200, Caddy 재시작 후 동일 인증서 복원을 확인했다. 현재 인증서 만료는 2027-02-01 12:53 KST다. 자동 갱신은 구성되어 있으나 실제 갱신 주기 관측은 아직 남아 있다.
- 신규 cloudflared connector를 실행해 QUIC 연결 4개와 DNS/UDP/TCP/API connectivity precheck 통과를 확인했다. 앱·PostgreSQL·Redis는 healthy, Caddy·Tunnel은 실행 중이다. host에 웹/DB/Redis 포트를 공개하지 않았다.
- 새 published application route는 `blog.codelily.kr` → `https://caddy:443`, originServerName/Host=`blog.codelily.kr`, noTLSVerify=false다. Cloudflare 단일 Service URL 입력 UI에서는 프로토콜을 포함한 전체 URL을 입력한다.
- 다음 작업: SJC 502 진단 → Google OAuth·R2·WAF 정책·외부 백업 인수. DNS/외부 PC HTTPS/CDN/private 응답 검증은 위와 같이 통과했다. 자동 인증서 갱신 관측과 수동 접근성 심사는 별도 대기다.
- 배포 검증에서 공용 egress를 공유하던 Tunnel이 Caddy의 egress IP로 해석되는 것을 발견했다. `tunnel_egress`/`caddy_egress`를 분리해 둘의 공통 네트워크를 `tunnel_link`로 한정했다. 실서버 connector namespace에서 `caddy`가 전용 주소 하나로만 해석되고 인증서 검증을 유지한 원본 HTTPS readiness가 200인 것까지 확인했다. Cloudflare Service URL은 `https://caddy:443`을 유지한다.

## 2026-11-03 운영 배포 준비

- 사용자 확인: iwinv Ubuntu 26 LTS 서버 구매, SSH inbound는 개발 PC만 허용, HTTP/HTTPS 및 outbound 방화벽 설정. 실제 OS·규칙은 서버 접속 후 검증한다. 가비아 도메인 등록과 Cloudflare 네임서버 위임은 완료됐으며 기존 `naraebi.codelily.kr`을 유지한다.
- 신규 `blog.codelily.kr` 전용 Tunnel·host별 보안/캐시 규칙과 outbound DNS 53/TCP·UDP 및 Tunnel 7844/TCP·UDP 확인을 [최초 배포 실행서](operations/iwinv-최초배포.md)에 작성했다. Node.js는 앱 이미지에 포함하고 Redis는 실제 사용 전까지 선택 profile로 유지한다.
- 운영 Compose에 신규 DB runtime/migrator/maintenance 초기화, post-migration 최소 권한 SQL, Redis 인증 healthcheck를 추가했다. `scripts/setup-production.mjs`는 기존 비밀값을 보존하며 새 env/secret을 만들고 값은 출력하지 않는다. Docker build context에서도 `.env`를 제외했다.
- 검증: 테스트 5개·모듈 경계·타입 검사 통과. 별도 실제 PostgreSQL 16/Redis에서 초기화·migration·healthcheck·runtime DDL/이력 쓰기 차단·maintenance의 회원/게시물 접근 차단 통과. Linux non-root 설정 생성과 디렉터리/secret/env의 0700/0444/0600 권한 통과. 임시 검증 컨테이너·볼륨은 정리했고 기존 개발 컨테이너는 유지했다.
- Windows 빌드는 기본 sandbox에서 산출물 생성 EPERM으로 실패했으나 동일 명령을 권한 조정 후 재실행하여 통과했다. 이번 변경에는 렌더링 UI 변경이 없으므로 브라우저 E2E는 재실행하지 않았다. 이전 E2E 5개 결과는 2026-11-02 기록이다.
- SSH 키 인증 완료. 실제 Ubuntu 26.04 LTS/amd64·2 CPU·약 8GB RAM 및 기존 웹/DB 서비스가 없는 신규 서버임을 확인했다. Docker 공식 APT 저장소로 Engine 29.9.2/Compose 5.7.0을 설치하고 hello-world를 실행했다. Node 24·고정 PostgreSQL16/Redis7·cloudflared 2026.10.7 이미지를 pull했다.
- Ubuntu 기본 chrony NTS의 4460/TCP가 시간 초과되어 동기화되지 않았다. 사용자가 ELCAP outbound 4460/TCP를 허용한 뒤 chrony를 재시작해 `NTPSynchronized=yes`, 정상 Leap 상태를 확인했다. 호스트 UFW는 없으며 iwinv 방화벽 규칙 원본은 별도 관리한다.
- 원격 저장소를 신규 배포 경로에 clone했다. 서버 접속 정보·개인키 경로·비밀값은 문서화하지 않는다. DNS·Cloudflare 계정에는 아직 변경하지 않았다.
- 운영 secret/env를 서버에서 생성했다. 개발 PC에서 앱·migrator·Caddy 2.11.7/Cloudflare DNS module v0.2.4 이미지를 빌드하고 SSH로 전송해 archive SHA-256과 image ID를 검증했다. 최초 배포는 registry 발행 없이 save/SCP/load 방식이며 [이미지 명세](../infra/releases/2026-11-03-bootstrap.json)에 버전을 기록한다. 호스트 유실 복구를 위해 검증 이미지의 외부 보관/registry 발행은 후속 과제다.
- 실제 서버의 `code-lily`·PostgreSQL·Redis 3개 컨테이너 healthy, migration·최소 권한 SQL·maintenance 실행 및 readiness 200 확인. `/posts`·`/about`·`/api/posts`도 200이고 공개 ISR 300초·개인 API no-store 헤더를 확인했다. 호스트에는 SSH와 시스템 DNS 등만 listen하며 앱/DB/Redis 공개 포트가 없다. 개발 seed는 운영에서 실행하지 않았다.
- 관측 시점 idle 메모리: 앱 약 65.8MiB/512MiB, DB 약 41.3MiB/1536MiB, Redis 약 3.5MiB/256MiB. 부하 측정이나 운영 용량 보장은 아니다.
- Caddy 설정은 더미 token을 사용한 validation을 통과했으며 실제 인증서는 아직 발급하지 않았다. `scripts/configure-cloudflare-secrets.sh`를 서버에 준비했고 token은 대화형 숨김 입력으로만 받는다. Tunnel outbound 7844/TCP 도달을 확인했으나 실제 Tunnel 인증/QUIC/원본 TLS는 미검증이다.
- 비밀 입력 도구는 실 token과 분리한 임시 디렉터리/가상 터미널에서 Bash 구문·비대화형 차단·입력값 비출력·원자적 저장·0444 권한을 검증했다. DNS API token 형식도 저장 전 확인한다.
- Cloudflare 공식 안내와 사용 중인 Caddy DNS module v0.2.4 소스를 확인해 API token 입력 검증을 기존 35~50자 및 신규 `cfut_`/`cfat_` 형식에 맞췄다. 발급 위치는 개발 PC 브라우저, 저장·사용 위치는 운영 서버 secret/컨테이너다.
- 다음 순서: 실제 Cloudflare token 등록 → Caddy 인증서 → 신규 Tunnel/hostname → Google/R2 및 백업 인수. 운영 인수 미완료이며 공개 배포 성공으로 표시하지 않는다.

- 추가 동기화: 개발 서버가 생성한 `apps/code-lily/next-env.d.ts`의 `.next/dev/types` 참조를 반영했다. `npm run typecheck`와 `git diff --check`를 통과했다. 기능 변경은 없으며 외부 연동 대기 항목과 다음 시작점은 아래와 같다.

## 이번 작업 기록

- 기존 4GB/6앱 예제는 과거 검토 자료로 보존한다. 현재 구현 기준은 `architecture/결정기록.md` 및 `infra/`다.
- 루트 AGENTS와 프로젝트별 재개 문서를 작성했다.
- 사용자 지시에 따라 로컬 Docker Desktop `desktop-linux`의 기존 컨테이너 5개·볼륨 4개·이미지 6개를 초기화했다. 재사용 가능한 setup에 전역 삭제 명령을 넣지 않았다.
- Root `compose.yaml`로 PostgreSQL 16·Redis를 새로 만들고, 실제 migration/runtime 역할 분리·DDL/교차 스키마 차단·migration 이력 쓰기 차단·Redis ACL을 확인했다.
- 운영 `infra/compose.production.yml`에 app·DB·Caddy·Tunnel과 `tools` profile의 migration/maintenance를 분리했다. 공개 host port는 없다.
- Windows standalone 빌드·Linux Docker 이미지 빌드, 타입/모듈 경계, 단위·SQL 통합 4개, 실제 Chrome E2E 5개 통과. Docker DB에서 실제 게시물 DML도 검증했다.
- E2E는 격리된 서명 세션과 임베디드 PostgreSQL wire fixture를 사용한다. 실제 Google provider 인증은 하지 않았으며 운영 계정으로 위장하는 route를 만들지 않았다.
- E2E 환경 `http://localhost:3000`, desktop 1440×1100 / mobile 390×844, Browser 플러그인 미설치로 Playwright Chrome 사용. 공개 페이지·편집기·관리 Chart/Grid의 자동 접근성 검사와 검색 모달 초점·Escape 복귀 통과.
- `x-nextjs-cache: HIT`, `s-maxage=300`, 글 공개 해제 후 404를 실제 standalone 응답으로 확인했다.
- 첨부 원본/생성 콘셉트/브라우저 screenshot의 팔레트·header·sidebar·카드·타이포·About·모바일 구조를 비교했다. brand/콘텐츠·터치 영역·보조 글자 대비·모바일 2줄 header는 의도적 변경이다.
- 초기 예시 글 6개와 About을 제공했다. 실제 개인 이력·프로필·공개 연락처로 교체한 뒤 운영한다.
